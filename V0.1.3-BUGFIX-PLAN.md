# evorift v0.1.3 — Bugfix Plan
_Generated 2026-06-11_

## TL;DR — "Is it a virus?"

**No. evorift is not a virus, and it is not infected.** What you (and your users) are seeing is a real but ordinary performance bug: the app asks Windows "which apps are using the network and what domains have they reached?" by repeatedly launching the heavyweight Windows scripting tool **PowerShell** — once for *every* protected app, *every couple of seconds*, forever, even when the window is minimized to the tray. Each PowerShell launch drags in the entire .NET runtime (1–3 seconds of CPU just to start) and also spins up a helper window-host process (`conhost.exe`). Because the app keeps firing new ones before the old ones finish, they **pile up into hundreds of short-lived processes** and peg the CPU. It *looks* exactly like malware — and that resemblance is itself a problem (antivirus engines flag this pattern) — but it is your own polling loop being far too aggressive. The fix is to stop launching PowerShell at all and read the same data directly from Windows in-process. The good news: the codebase is already wired for the native Windows APIs needed, so the fix is mechanical, not architectural.

One important nuance: the *specific* processes you counted (≈348 `tasklist.exe`, ≈290 `cmd.exe`) are **not** evorift's — evorift launches no `cmd.exe` and only one (dead, never-called) `tasklist`. Those almost certainly belong to the **official Cloudflare WARP / Cloudflare One client**, which polls `tasklist /FO CSV`. evorift's fingerprint is the `powershell.exe` + `conhost.exe` pairs (and bursts of `sc.exe`/`taskkill.exe`). So **both** are spawning processes; the section below pins down exactly which is which.

## 🔴 Critical bug: process pileup / 100% CPU

### Definitive verdict

**evorift IS a real contributor to the pileup — it is its own bug, not solely the Cloudflare client.** The audit traces evorift's contribution to two persistent loops, with one dominant offender:

1. **PRIMARY — the UI per-app domain-watch loop** (`src/lib/state.svelte.ts:417` `#startDomainWatch` → `invoke("detect_app_domains")` → `src-tauri/src/lib.rs:163`/`:330` `detect_domains_blocking`). This spawns **one `powershell.exe` (+ its `conhost.exe`) per non-"off" app, per tick**, continuously while protection is on.
2. **SECONDARY — the service watchdog** (`src-tauri/src/service.rs:954`) calling `src-tauri/src/pid_scan.rs:55` (one `powershell.exe` per 5 s when "off"-mode apps exist), plus bursty `sc.exe`/`taskkill.exe` storms from the winws restart path (`src-tauri/src/engine.rs:199`, `:214`).

**Who spawns what (evidence-based attribution):**

| Process you observed | Source | evorift's fault? |
|---|---|---|
| `powershell.exe` (many) | evorift domain-watch (`state.svelte.ts:417`) + service pid_scan (`pid_scan.rs:55`) | **YES — evorift** |
| `conhost.exe` (≈367) | Every console child evorift spawns gets one; **also** every Cloudflare `tasklist` gets one | **BOTH** (shared symptom) |
| `sc.exe` / `taskkill.exe` (bursts) | evorift winws restart path (`engine.rs:199`, `:214`) | **YES — evorift** |
| `tasklist.exe` (≈348) | evorift's only `tasklist` is **dead code, never called** (`lib.rs:394` `detect_anticheat`) | **NO — Cloudflare One client** |
| `cmd.exe` (≈290) | evorift launches **no `cmd.exe` anywhere** | **NO — Cloudflare One client** |

So the user's original instinct was **half right**: the `tasklist`/`cmd` flood is Cloudflare's process monitor, but the `powershell`/`conhost`/`sc`/`taskkill` churn — and a large share of the CPU pegging — is **evorift's own domain-watch loop**.

### Root cause #1 (dominant): UI domain-watch — `src/lib/state.svelte.ts:417`

- **Cadence:** recursive `setTimeout`, adaptive floor `DW_BASE = 2000 ms` → ceiling `DW_MAX = 5000 ms`, backing off ×2 every 3 min (`DW_STEP_MS = 180_000`). (The doc comment at `state.svelte.ts:396–404` still says "100ms" — it is **stale**; the partial fix to 2000 ms landed.)
- **Per-tick cost:** when `app.status === "on"`, it loops over **every** app in `this.apps` and, for each with `mode !== "off"` and an `exe` (`state.svelte.ts:430–435`), calls `#detectAndAdd(r)` → `invoke("detect_app_domains")` → backend `detect_domains_blocking` (`src-tauri/src/lib.rs:330`) which **spawns one `powershell.exe`** running `Get-Process` + `Get-NetTCPConnection` + `Get-DnsClientCache` + `Resolve-DnsName` (all heavy). **No cap on apps-per-tick.**
- **The floor-pinning trap:** any newly-found domain calls `#resetDomainWatch()` (`state.svelte.ts:441`) which snaps the interval back to the 2 s floor. Apps like Chrome and Discord open new connections constantly, so the loop **never backs off to 5 s** — it stays pinned at 2 s.
- **Never pauses when hidden:** there is no `document.hidden`/visibility check. Since `autoProtect` + `startMinimized` default to true, this loop **runs forever in the background even when minimized to tray.**
- **The guard limits concurrency, not rate:** `#dwRunning` (`state.svelte.ts:415`) prevents one full sweep from overlapping the next, and apps within a tick are awaited sequentially — but it does **not** cap the absolute spawn rate or apps-per-tick.

### Per-second spawn math

Every `powershell.exe` also spawns a `conhost.exe`, so multiply PS counts by 2.

- `list_apps` returns **every process with an active TCP/listening-UDP socket** — easily **30–80 apps** on a busy machine. New apps default to `mode:"off"`, but the seeded defaults (Discord, Roblox, **Chrome = `dpi`**) plus anything the user flips on all get scanned.
- At the pinned 2 s floor with **N** dpi/warp apps: **N PowerShell + N conhost every 2 s**.
- With **N = 10**: 10 PS + 10 conhost / 2 s = **5 powershell/s + 5 conhost/s = 10 processes/s**.
- Each PowerShell 5.1 cold start is **1–3 s of CPU** (full .NET CLR load) plus profile/module/PSReadLine load and possible 15 s CRL-check stalls. At 5/s these overlap heavily → **sustained ~100% across several cores**, matching the i7-275HX pegging.
- **Why the pileup compounds:** when a tick's work takes *longer* than the interval (which it will under CPU load), spawns drain slower than they arrive → positive-feedback runaway. This is exactly why raising the interval to 2000 ms **alone did not fix it** — the spawn itself is the problem, not the interval.

### Root cause #2 (secondary, bursty): winws restart storm + pid_scan

- **`pid_scan.rs:55`** — one `powershell.exe` (+conhost) every 5 s, but **only** while a running app is in "off" mode with a known path. Steady but low (~0.2 PS/s).
- **`engine.rs:214` `clear_stale_windivert`** — up to **~21 `sc.exe` spawns per winws (re)start** (≈3 driver names × query + maybe stop + ≤5 retry polls + delete, with 500 ms sleeps), plus **`engine.rs:199` `taskkill /f /im winws.exe`** (1 per start). If the "off"-app set *flaps* (ports churn every 5 s), the watchdog forces repeated winws restarts → a **~20-process `sc`/`taskkill`/`conhost` burst every 5 s.**

### Cleared (NOT a cause)

- **Anti-cheat watcher** — `detect_anticheat()` (`lib.rs:394`) is **dead code**: defined once, never called, no thread, no `#[tauri::command]`, no caller. The removal commit is verified. This is the only `tasklist` in the codebase. **It cannot contribute to the pileup.**
- `connectivity_test` (`lib.rs:103`, raw `TcpStream`), the telemetry subscribe thread (`lib.rs:729`, pure IPC), `BinaryRain` (15 fps canvas), `BlackHole` (WebGL rAF) — **none spawn any process.**

### Misattribution to correct

The current CHANGELOG/README "Known Issues" note that blames the Cloudflare WARP client for the CPU problem is **partially wrong and must be corrected.** It is true the `tasklist`/`cmd` flood is Cloudflare's, but that note **lets evorift's own domain-watch loop off the hook**. evorift's `powershell.exe`/`conhost.exe`/`sc.exe` churn is a genuine evorift bug and the dominant CPU source. The note should be rewritten to say: *evorift's own per-app domain-watch loop was the primary cause (fixed in 0.1.3); the Cloudflare One client additionally runs its own `tasklist` monitor.*

## ✅ Fix plan: the CPU bug

### (a) IMMEDIATE mitigation — stop the bleeding (ship today)

1. **[S, HIGH] Gate the domain-watch loop on window visibility + only-while-needed.** Pause `#startDomainWatch` when `document.hidden` (minimized/tray) and resume on `visibilitychange`. Since the app auto-minimizes to tray, this alone removes the vast majority of background spawns. *(Pattern: the same `visibilitychange` cancel already used by `BlackHole.svelte:297`.)* — Ref: [Tdarr #1323](https://github.com/HaveAGitGat/tdarr/issues/1323).
2. **[S, HIGH] Cap apps-per-tick and stop floor-pinning.** Scan at most a small number of apps per tick (round-robin), and **do not** call `#resetDomainWatch()` on every newly-found domain — let the backoff actually reach 5 s. Add a per-app cooldown so an app isn't re-scanned within, say, 30–60 s of its last successful scan. — Ref: [Tdarr fix: cache + skip on no-change](https://github.com/HaveAGitGat/tdarr/issues/1323), [Debounce vs Throttle](https://kettanaito.com/blog/debounce-vs-throttle).
3. **[S, HIGH] Raise the real cadence to 5–30 s.** Sub-second/2 s polling is far too aggressive for data that changes on the order of seconds-to-minutes; documented guidance for process-monitoring loops is **≥60 s**. — Ref: [Tdarr #1323](https://github.com/HaveAGitGat/tdarr/issues/1323).
4. **[S, MED] Bound the winws restart storm.** Debounce "off"-set changes so port-flapping does not force repeated winws restarts, and cache the last-applied exclusion set so the watchdog only restarts winws on a *real* change (it already has an idempotency check on the child handle — extend it to the exclusion set). This collapses the `sc`/`taskkill` bursts. — Ref: cache+skip pattern, [Tdarr #1323](https://github.com/HaveAGitGat/tdarr/issues/1323).
5. **[S, LOW] Add `-NoProfile -NoLogo` to any PowerShell that must remain temporarily.** Cuts profile/module cold-start cost while the proper fix lands. — Ref: [PowerShell startup performance](https://learn.microsoft.com/en-us/powershell/scripting/dev-cross-plat/performance/startup-performance), [woshub](https://woshub.com/powershell-slow-startup/).

### (b) PROPER fix — replace PowerShell/tasklist with native Win32 APIs

This is the real cure: **eliminate the console-process spawns entirely.** `CREATE_NO_WINDOW` (already set everywhere) hides the *window* but does **not** prevent the `conhost.exe` child — only not spawning a console process does. The project **already depends on `windows-sys 0.52` with `Win32_NetworkManagement_IpHelper`, `Win32_System_Threading`, `Win32_System_JobObjects`, `Win32_Foundation` enabled** (`src-tauri/Cargo.toml:40`) and **already calls IP Helper natively** (`GetIfTable2`/`FreeMibTable` at `service.rs:678`) and **already uses kill-on-close Job Objects** (`engine.rs:160–192`). The replacements follow that exact, proven pattern — **zero new crates, zero new feature flags** (except optional Toolhelp).

1. **[M, CRITICAL] Replace all socket/PID enumeration with `GetExtendedTcpTable` / `GetExtendedUdpTable`.** One call returns the entire socket→PID map (local/remote IP+port + owning PID) for every process — no per-app loop, no PowerShell. Run once for `AF_INET` and once for `AF_INET6`. Two-pass size pattern (NULL buffer → size → real buffer). This replaces `pid_scan.rs:55`, `list_apps_blocking`, and the socket half of `detect_domains_blocking`.

   ```rust
   use windows_sys::Win32::NetworkManagement::IpHelper::{
       GetExtendedTcpTable, MIB_TCPTABLE_OWNER_PID, MIB_TCPROW_OWNER_PID, TCP_TABLE_OWNER_PID_ALL,
   };
   const AF_INET: u32 = 2;
   let mut size = 0u32;
   GetExtendedTcpTable(std::ptr::null_mut(), &mut size, 0, AF_INET, TCP_TABLE_OWNER_PID_ALL, 0);
   let mut buf = vec![0u8; size as usize];
   let rc = GetExtendedTcpTable(buf.as_mut_ptr() as *mut _, &mut size, 0, AF_INET, TCP_TABLE_OWNER_PID_ALL, 0);
   // table.dwNumEntries, slice from table.table[0]; ports are network byte order (.to_be() on u16)
   ```
   — Refs: [GetExtendedTcpTable (windows-sys)](https://docs.rs/windows-sys/latest/windows_sys/Win32/NetworkManagement/IpHelper/fn.GetExtendedTcpTable.html), [MIB_TCPTABLE_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcptable_owner_pid), [MIB_UDPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/udpmib/ns-udpmib-mib_udprow_owner_pid), [killport two-pass impl](https://jacobtread.com/blog/killport/).

2. **[M, CRITICAL] Resolve PID → exe path with `QueryFullProcessImageNameW`.** Open with `PROCESS_QUERY_LIMITED_INFORMATION` (0x1000 — minimal right, works cross-bitness and for other users from the elevated service), query, `CloseHandle`. Replaces the `Get-Process` path-resolution work.

   ```rust
   use windows_sys::Win32::System::Threading::{OpenProcess, QueryFullProcessImageNameW, PROCESS_QUERY_LIMITED_INFORMATION};
   use windows_sys::Win32::Foundation::CloseHandle;
   let h = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, 0, pid);
   let mut buf = [0u16; 1024]; let mut len = buf.len() as u32;
   let ok = QueryFullProcessImageNameW(h, 0, buf.as_mut_ptr(), &mut len);
   CloseHandle(h);
   ```
   — Refs: [QueryFullProcessImageNameW (windows-sys)](https://docs.rs/windows-sys/latest/windows_sys/Win32/System/Threading/fn.QueryFullProcessImageNameW.html), [OpenProcess](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/System/Threading/fn.OpenProcess.html).

3. **[M, HIGH] Replace `Get-DnsClientCache` with in-process `DnsGetCacheDataTable` (defensive).** Undocumented `dnsapi.dll` export (the one `ipconfig` uses); walks a linked list of cached names + record types. Returns **names, not IPs** — resolve each via cache-only `DnsQuery_W` if an IP is needed. Treat as best-effort with graceful fallback (it is undocumented and has shifted across builds). — Refs: [muhdnscache](https://github.com/FRex/muhdnscache), [malcomvetter/DnsCache struct](https://github.com/malcomvetter/DnsCache/blob/master/DnsCache/DnsCache.cpp), [DnsGetCacheDataTable reference](http://filelog.net/func/DnsGetCacheDataTable).

4. **[S, MED] Use Toolhelp (`CreateToolhelp32Snapshot` + `Process32FirstW/NextW`) only if a PID→name table is needed** beyond what §1+§2 give. This is the **one new feature flag** (`Win32_System_Diagnostics_ToolHelp`) and is optional. Use the **W** variants + `from_utf16_lossy`; set `pe.dwSize` before the first call. — Refs: [CreateToolhelp32Snapshot (windows-sys)](https://docs.rs/windows-sys/latest/windows_sys/Win32/System/Diagnostics/ToolHelp/fn.CreateToolhelp32Snapshot.html), [Rustware Part 2](https://syrion.me/rustware-part-2-process-enumeration-development/).

5. **[M, MED] Accept that per-app domain detection is fundamentally impossible for DoH browsers — and stop trying to brute-force it.** Chrome/Edge/Brave ship their own DNS stub resolver (`net::DnsClient` + `net::HostCache`) and, with Secure DNS/DoH on (now common-default), **bypass the OS resolver entirely** — so their domains *never* enter the Windows DNS cache. Cache-based detection silently fails for exactly the apps with the most domains. For browsers, fall back to **TLS SNI** (which the winws/zapret datapath already inspects — though ECH is eroding this) or, preferably, **fixed hostlists / IP-range matching** (the strategy the DPI engine already uses). Do not keep a heavy live-discovery loop fighting this. — Refs: [Chromium net/dns/README](https://chromium.googlesource.com/chromium/src/+/main/net/dns/README.md), [BlackFog async DNS](https://www.blackfog.com/knowledge-base/disable-async-dns-on-google-chrome-for-windows/), [Cloudflare ECH](https://blog.cloudflare.com/encrypted-client-hello/), [RFC 9849](https://datatracker.ietf.org/doc/rfc9849/).

6. **[S, MED] Reverse DNS (`GetNameInfoW`) only as a cached hint, never per-connection on a loop.** It is blocking, times out on failure, and for CDN-fronted services (Discord/YouTube/Roblox on Cloudflare/Google) returns useless `*.1e100.net`-style PTRs, not the user domain. Microsoft itself calls reverse lookups "inherently unreliable… use only as a hint." — Refs: [GetNameInfoW](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getnameinfow), [getnameinfo delays IBM PQ86472](https://www.ibm.com/support/pages/apar/PQ86472).

### (c) Structural hardening (do alongside the rewrite)

1. **[M, HIGH] Single-flight + correct timer behavior on every remaining loop.** Frontend: a true `Promise`/boolean in-flight guard covering the whole async chain. Backend service loop: if it moves to tokio, use `tokio::time::interval` with **`MissedTickBehavior::Skip`** (the default `Burst` *creates* pileups by firing the backlog as fast as possible); or keep a single `std::thread` with `recv_timeout`/`Condvar` (inherently single-flight + wakeable for shutdown). **Never run blocking work directly on the async runtime** — use `spawn_blocking`. — Refs: [tokio Interval](https://docs.rs/tokio/latest/tokio/time/struct.Interval.html), [MissedTickBehavior](https://docs.rs/tokio/latest/tokio/time/enum.MissedTickBehavior.html), [tokio #3574](https://github.com/tokio-rs/tokio/issues/3574), [tokio #4730](https://github.com/tokio-rs/tokio/issues/4730).
2. **[S, MED] Wrap every remaining helper child (winws, wgcf, wireguard, sc, netsh) in a kill-on-close Job Object.** `CreateJobObject` → set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` → `AssignProcessToJobObject`; assign the service's own process so a crash/kill can never leave orphaned CPU-pegging children (the "virus residue"). The pattern is **already implemented for winws** (`engine.rs:160–192`) — generalize it. — Refs: [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Meziantou kill-on-close](https://www.meziantou.net/killing-all-child-processes-when-the-parent-exits-job-object.htm), [cargo job.rs](https://doc.rust-lang.org/nightly/nightly-rustc/src/cargo/util/job.rs.html).
3. **[S, LOW] Delete the dead `detect_anticheat()` + `AntiCheat` struct + `ANTICHEAT_PROCS`** (`lib.rs:372–403`). It is the only `tasklist` in the tree; removing it eliminates the one remaining mass-`tasklist` foot-gun and a malware-heuristic trigger.

> **Why this is a shipping requirement, not just an optimization:** mass-spawning `cmd.exe`/`powershell.exe`/`tasklist` from a non-shell parent is a **primary AV/EDR malware heuristic** (Defender behavioral monitoring, Elastic "Unusual Parent Process for cmd.exe", Rapid7 suspicious-process rules). For a brand-new network tool, every false-positive **damages SmartScreen/publisher reputation**, which takes weeks + hundreds of clean installs to build — and **EV certs no longer auto-bypass SmartScreen.** Removing the spawns removes the single biggest reputation liability. — Refs: [Threat Hunting: cmd/powershell spawns](https://medium.com/@balasubramanya.c/threat-hunting-series-1-3-prohibited-applications-spawning-cmd-exe-or-powershell-exe-a9bb3ffae8b6), [Elastic: Unusual Parent Process for cmd.exe](https://www.elastic.co/guide/en/security/8.19/unusual-parent-process-for-cmd-exe.html), [Rapid7 Windows Suspicious Process](https://docs.rapid7.com/insightidr/windows-suspicious-process/), [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), [DigiCert EV+SmartScreen](https://knowledge.digicert.com/alerts/ev-signed-application-showing-microsoft-defender-smartscreen-warnings).

## WARP full protection (full-tunnel) — diagnosis & fix plan

### How it is wired today

`applyFullProtection()` (`state.svelte.ts:477`) sets `fullProtection=true`, sends IPC `set_full_warp{enable:true}`, then `toggle()` if off. IPC `Command::SetFullWarp` passes a no-op `validate()` (`ipc.rs:197`). Service `dispatch` sets `e.full_warp=true` (`service.rs:256`) → `warp_target()` returns `Some(true)` → `e.warp.start(true)` (`service.rs:259–266`). `WarpEngine::start(full=true)` (`warp.rs:118`) regenerates `warp.conf` with `FULL_ALLOWED_IPS = "0.0.0.0/0, ::/0"`, fixed `Endpoint = 188.114.98.224:2408`, **DNS stripped**, and installs via `wireguard.exe /installtunnelservice` (service `WireGuardTunnel$warp`).

### Why it does NOT route all traffic like the Cloudflare One client

The `.conf` is *mostly* correct (`0.0.0.0/0, ::/0`, MTU 1280, correct WARP endpoint/key). The divergences, in priority order:

1. **[CRITICAL] DNS is stripped in full mode — the biggest functional bug.** `split_tunnel_config` deletes every `DNS=` line (`warp.rs:70–72`) for **both** modes. That is correct for *split* tunnel (keep system DoH authoritative) but **wrong for full tunnel**. A Cloudflare-style full tunnel must pin tunnel DNS (`DNS = 1.1.1.1, 1.0.0.1, 2606:4700:4700::1111, 2606:4700:4700::1001`). With `0.0.0.0/0` and **no `DNS=`**, the default route flips into the tunnel but resolution has no in-tunnel resolver → classic "connected but no internet / pages don't load." **Fix: branch the config builder so full mode keeps `DNS=`; only split mode strips it.** — Refs: [Pro Custodibus DNS troubleshooting](https://www.procustodibus.com/blog/2023/09/troubleshooting-wireguard-dns-issues/), [cr0x.net WireGuard DNS](https://cr0x.net/en/wireguard-dns-not-working/), [Acciyo no-internet fix](https://www.acciyo.com/fixing-your-wireguard-tunnel-when-it-says-no-internet-access/), [wgcf README](https://github.com/ViRb3/wgcf), [E2Encrypted](https://www.e2encrypted.com/howtos/cloudflare-warp-via-wireguard/).

2. **[HIGH] The auto kill-switch is misunderstood — and may be silently breaking DNS.** WireGuard-for-Windows **automatically installs a WFP kill-switch whenever any AllowedIP is `/0`** (the `/0` condition alone triggers it; a `DNS=` line is *not* required to enable it). It permits only tunnel-service traffic, loopback, DHCP/NDP, in-tunnel traffic, and — *only if `DNS=` is configured* — DNS to those exact servers. So evorift's full tunnel currently has the kill-switch **on** but **no whitelisted resolver**, blocking the very DoH it relies on. **Fix: supply tunnel `DNS=` (whitelisted by the kill-switch); if the kill-switch must be avoided, use `0.0.0.0/1, 128.0.0.0/1` instead of `0.0.0.0/0` (same coverage, no `/0` trigger).** — Ref: [wireguard-windows netquirk.md](https://git.zx2c4.com/wireguard-windows/tree/docs/netquirk.md).

3. **[HIGH] Do NOT add a manual endpoint /32 — and stop expecting a visible one.** The `warp.rs:25–28` comment expects wireguard.exe to "auto-add a /32 exclusion route for the endpoint." It is *directionally* right that the handshake egresses the physical NIC automatically, but the mechanism on Windows is **socket-marking + default-route monitoring** ("WireGuardNT monitors the routing table and determines the outgoing route that does not loop back to itself"), **not** a visible /32. Adding one yourself fights the monitor. If handshake fails, the cause is items 1/5/6, not a missing /32. — Refs: [netquirk.md](https://git.zx2c4.com/wireguard-windows/tree/docs/netquirk.md), [WireGuard netns](https://www.wireguard.com/netns/).

4. **[HIGH] winws/WinDivert running *in front of* the tunnel can corrupt traffic.** During full protection winws is **still running** (`set_full_warp` never stops the DPI engine). WinDivert captures at `WINDIVERT_LAYER_NETWORK` — the **plaintext** layer — and can see the app's original 443/QUIC packets on the wintun adapter **before** WireGuard encrypts them. Mangling a packet that is about to be encrypted corrupts the inner payload → far end drops it → "connected but nothing loads." In full mode winws is **redundant** (100% of traffic is already encrypted). **Fix: disable winws while full WARP is active (restore on exit), or at minimum pin its WinDivert filter to the physical adapter's `IfIdx` and exclude the wintun adapter + the `UDP/2408` endpoint flow.** — Refs: [WinDivert docs](https://www.reqrypt.org/windivert-doc.html), [Wintun (L3 TUN, plaintext IP)](https://www.wintun.net/).

5. **[HIGH] Failures are swallowed — the UI claims "Tam Koruma" even when no tunnel exists.** Every `warp.start()` caller only audits-and-continues (`service.rs:153, 246, 262`; warp.rs "errors non-fatal"), and `e.full_warp`/UI `fullProtection` flip to true **regardless of whether `/installtunnelservice` succeeded.** Worse, if the bundled `wireguard.exe`/`wintun.dll` is **missing** (the Engine-B memory note says the WARP binaries were *intentionally not committed*, so shipped machines may lack them), `start()` takes the **sim no-op path** (`warp.rs:120–128`), sets `running=true`, and **no tunnel exists at all** — pure no-op "full protection." **Fix: verify the tunnel actually reaches Connected (check latest-handshake) before reporting success; detect the missing-bundle sim path; surface install errors to the UI instead of audit-and-continue.**

6. **[MED] IPv6 must actually route.** `::/0` is set, but v6 only tunnels if the wgcf profile's `Address = <v6>/128` interface line survives `split_tunnel_config` **and** the v6 default route installs. If the v6 address is dropped or the route isn't installed, v6 leaks out the physical NIC or stalls. **Fix: preserve the v6 `Address` /128; confirm the v6 default route installs.** — Ref: [wgcf README](https://github.com/ViRb3/wgcf).

7. **[MED] MTU clamp lever for restrictive ISPs.** wgcf's `MTU=1280` is the safe default (matches the official Android app). But in full mode *every* flow traverses the tunnel; if small packets work and large TLS/QUIC flows hang, that is PMTUD blackholing — lower MTU (1280→1200/1180) or clamp MSS. Cloudflare tunes this dynamically; evorift does not. — Refs: [wgcf README](https://github.com/ViRb3/wgcf), [wgcf #40 MTU 1280](https://github.com/ViRb3/wgcf/issues/40), [Technicus full-tunnel no internet](https://techblog.jeppson.org/2025/10/wireguard-client-full-tunnel-no-internet/).

8. **[MED] Watchdog does not reconcile mode.** The 5 s watchdog (`service.rs:978–986`) only starts WARP `if !is_running()` and stops on target `None`; the `_ => {}` arm explicitly does **not** repair a split↔full mismatch. A partially-failed transition is never corrected. Also, a crashed service can leave `WireGuardTunnel$warp` Running in the *wrong* mode. **Fix: reconcile mode (not just running/stopped) in the watchdog, and force-uninstall a leftover `WireGuardTunnel$warp` at startup before reinstalling.**

### What a correct full tunnel needs (summary)

Keep `DNS=` in full mode; rely on automatic endpoint exclusion (no manual /32); disable winws (or pin to physical IfIdx + exclude wintun/UDP-2408) in full mode; verify a real handshake before claiming success and surface errors; preserve v6 `Address` + confirm v6 route; expose MTU clamp; reconcile mode in the watchdog. The official Cloudflare client is the same WireGuard full tunnel — it differs only operationally (pins DNS, tunes MTU, manages v4+v6 routes, has **no DPI mangler in front**, reports connected only after a real handshake). — Refs: [Project X WARP-via-WireGuard](https://xtls.github.io/en/document/level-2/warp.html), [netquirk.md](https://git.zx2c4.com/wireguard-windows/tree/docs/netquirk.md).

## UI behavior: BinaryRain + BlackHole — desired vs current + plan

### Desired

- **(a)** In full protection: show falling 0/1 + black hole **only while the connection actually works**; otherwise blank.
- **(b)** On error / servers unreachable: a **5–10 s "loading" binary animation** signalling something is loading.
- **(c)** Full protection OFF + DPI+WARP working fine: black hole **may** show.

### Current behavior

- **BinaryRain.svelte** — gate `{#if app.fullProtection}` (line 91); 2D canvas `setInterval` at **15 fps** (`FPS=15`). **Bug: it is mounted TWICE** — `+layout.svelte:53` AND `+page.svelte:13` — so when full protection is on there are **two full-screen canvases + two 15 fps intervals.** It reads only `fullProtection`, never any health signal, never `activating`. Does **not** pause on `document.hidden`. No subprocess. The component comments ("01 yağmuru bunu izler") are **stale** — wiring changed to `fullProtection`.
- **BlackHole.svelte** — mounted once (`+page.svelte:84`); the power button. `reduceMotion` → static SVG; else three.js WebGL with a **300-step-per-pixel Schwarzschild raymarch** at ~60 fps (the single heaviest render in the app; GPU-bound, **not** a spawn source). Pauses on `document.hidden` (line 297). Its disk lights from `activeTarget` (line 187) = 1 when `app.status` is `"on"`/`"connecting"` — i.e. purely from **intent**, NOT from real connectivity.

### The missing signal — the core gap

There is currently **no frontend-visible "connection actually works" boolean and no WARP-tunnel-up signal over IPC.** The raw ingredients all exist but are unused by the visuals:

- **Real reachability already streams every second:** telemetry `ping`/`loss` (TCP RTT to 1.1.1.1:443, `service.rs:757–764`) → `app.ping`/`app.loss`. `app.ping > 0 && app.loss < 100` is a genuine health signal — but nothing in BlackHole/BinaryRain reads it.
- `connectivity_test` (`lib.rs:97`, real DNS+TCP probe) exists but is **only one-shot** from Onboarding/Logs — never polled.
- `m.running` in telemetry = `engine.running` (winws started), **not** a connectivity verdict.
- Service-side `warp.is_running()` (`service.rs:979`) is **never exposed to the UI over IPC.**

### Plan

1. **[S, HIGH] Fix the double-mount of BinaryRain.** Mount it in exactly one place (`+layout.svelte` *or* `+page.svelte`, not both). Eliminates the duplicate canvas + interval immediately.
2. **[M, HIGH] Add a derived `app.healthy` flag in `state.svelte.ts`.** Define it as: last telemetry received within ~2 s **AND** `app.loss < 100` **AND** `app.ping > 0`. This is the "connection actually works" boolean the desired behavior needs, built from signals that already stream.
3. **[M, MED] Surface real WARP-up state over IPC.** Add a query/event exposing service-side `warp.is_running()` + (ideally) latest-handshake, so full-protection health is grounded in the tunnel actually being up — not just the optimistic `fullProtection` intent flag (ties into WARP fix #5 above).
4. **[S, HIGH] Re-gate the visuals on health (desired (a)/(c)):**
   - BinaryRain: `{#if app.fullProtection && app.healthy}` (rain only while full protection genuinely works).
   - BlackHole: feed `app.healthy` (not raw `status`) into `activeTarget`, so the disk lights only when the connection actually works. Case (c) — full protection off, DPI+WARP fine — is then naturally satisfied because `healthy` is true.
5. **[M, MED] Add a loading/error state for desired (b).** Introduce a `loading`/`error` signal driven by `connectivity_test` failing or telemetry showing `loss === 100`/stale; on that signal, switch BinaryRain to a **5–10 s timed "loading" animation** (it currently never reads `activating` or any error state). Wire the existing-but-unused `activating` flag or a new explicit flag.
6. **[S, LOW] Pause BinaryRain on `document.hidden`.** Match BlackHole's `visibilitychange` handling so neither visual burns CPU/GPU while minimized (relevant to the CPU-pegging *feeling*, though neither spawns processes).

> Note: per CLAUDE.md, `BlackHole.svelte` is developed in a separate chat — this is analysis only; coordinate before editing it. Neither BinaryRain nor BlackHole spawns any OS process; they are pure in-renderer loops and are **not** part of the process pileup (only steady CPU/GPU render load, worsened by the duplicate BinaryRain mount).

## Other latent issues

- **[MED] Error-swallowing across the WARP path** (`service.rs:153, 246, 262`; warp.rs "non-fatal"). State is set to success regardless of actual outcome. Surface failures to the UI; do not flip `fullProtection`/`running` on a failed install. (Same root issue as WARP #5.)
- **[MED] No Job-Object cleanup for non-winws children.** winws is wrapped (`engine.rs:160–192`), but `wgcf.exe`, `wireguard.exe`, `sc`, `netsh`, `taskkill` are not — a crashed service can orphan them. Generalize kill-on-close (see CPU fix (c)2).
- **[MED] `clear_stale_windivert` is an unbounded-ish burst** (`engine.rs:214` — up to ~21 `sc` spawns with 500 ms sleeps **per** winws start). The sleeps also stall the watchdog thread. Cache the cleared state; only run on a *real* (re)start.
- **[LOW] Stale comments mislead future maintainers:** `state.svelte.ts:396–404` still says "100ms" (actual 2000 ms); `BinaryRain.svelte` comments reference `activating` though it now reads `fullProtection`. Update during the fix.
- **[LOW] Dead code:** `detect_anticheat()` + `AntiCheat` + `ANTICHEAT_PROCS` (`lib.rs:372–403`) — remove (CPU fix (c)3).
- **[LOW] `DnsGetCacheDataTable` is undocumented/fragile** if adopted — wrap defensively with a graceful fallback; behavior has shifted across Windows builds (the `0x8000` flag discovery in muhdnscache). — Ref: [muhdnscache](https://github.com/FRex/muhdnscache).
- **[LOW] WMIC must never be (re)introduced** — Microsoft is removing it (gone as of Windows 11 25H2); any `wmic` shell-out would break on current Windows. Use the `wmi` crate in-process if WMI is ever needed.
- **[INFO] Telemetry/IPC loops are clean:** the 1 Hz telemetry loop (`service.rs:725`) uses in-process `GetIfTable2` + TCP, no spawns; the reconnect loop (`lib.rs:729`) is pure IPC; the named-pipe accept loop (`service.rs:991`) is event-driven. No action needed.
